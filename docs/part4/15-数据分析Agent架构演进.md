## 背景：一个比想象中复杂得多的"查数据"需求

延续案例一的项目，当数据查询能力接入真实的游戏数据报表平台后，我很快发现："让 LLM 查数据"这件事,比它听起来简单的表面复杂得多。同一个游戏在数据平台上有几十上百个报表，每个报表下又有几十个图表，用户的自然语言提问和这些报表/图表之间，需要一层精确的"翻译"。

## 第一版：全量拉取，让 LLM 自己从海量数据里找答案

最朴素的做法：用户问"这个游戏的举报情况"，直接把这个游戏下所有报表全部数据拉出来，扔给 LLM 去总结。**这是一个典型的"没有做检索、直接堆上下文"的反面案例**——对应 Part 3 第09章讲的"知识量能不能塞进一次上下文"的判断。

问题很快暴露：数据量太大，一个游戏几十个报表的全量数据远超单次上下文窗口；即便硬塞进去，Part 3 第10章讲的"Lost in the Middle"效应导致 LLM 经常抓不住真正相关的那几个数字，混在大量无关图表数据里，回答开始变得笼统、甚至张冠李戴。

### 🔒 完整版内容包含（购买后解锁）

- **智能报表匹配**的完整设计：为什么"关键词配置要充分覆盖同义词"（比如"推单"要同时配"推送/机器审核/机审推送"）是这个系统最容易踩的坑，一旦漏配同义词会导致用户换个说法就匹配不到精确报表，退化成场景级全量匹配，LLM 在海量数据中"迷失"
- **智能图表匹配**的实现：不是拉整个报表，而是精确定位到具体哪几张图表（`choose_chart_col` 参数设计），如何用 LLM 做图表级别的语义匹配而不只是报表级别
- **智能时间解析**：怎么让LLM 稳定解析"上个月""去年11月""近30天""12月上旬"这类自然语言时间表达，包括必须"写死当前日期"这个反直觉的细节（为什么不能依赖模型自己判断当前日期）
- **错误检测机制**：API异常/数据为空/全0数据分别怎么识别并给出正确的提示，而不是让 LLM 把"查询失败"误判成"这个指标确实是0"
- 完整的场景配置体系：怎么设计"报表-场景"两层结构，让用户既能精确查询单个报表，也能做泛化的场景级分析
