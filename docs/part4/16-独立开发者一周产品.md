## 背景：一个真实的"读书类" AI 小产品

转型做独立 AI 产品手艺人之后，我做过一个叫"读书行动派"的小产品：输入书名或拍一张封面照片，AI 识别书籍后生成解读，用户再填一些个人信息（身份角色、当下具体问题），生成一份**个性化**的深度解读+行动清单，最后一键生成分享图。

这个案例最有价值的地方，不是产品创意本身，是**一个独立开发者从"本地能跑"到"任何人都能打开"要经历的全部真实阶段**——这条路上的坑，比写Agent 逻辑本身更容易被低估。

## 第一版：Flask + 内网服务器，验证核心逻辑

MVP 用 Flask 写后端 + 纯前端单页，部署在一台云服务器上。核心设计决策：

- 只让用户输入书名或拍封面，不要求上传全文电子版——规避版权风险
- 同一本书的基础解读做本地缓存复用，降低成本（这是"记忆与检索"思想在成本控制上的应用，对应 Part 3 第09章）
- 个性化信息如果为空，模型一开始会"直接忽略"当成可选项——**这是一个典型的 Prompt 工程问题**，后来改成强制规则块，要求模型自我检查"去掉这些个人信息，输出会不会完全一样"

### 🔒 完整版内容包含（购买后解锁）

- **从内网到公网的完整迁移决策过程**：依次尝试了哪些云服务方案、每个方案失败的具体原因（端口冲突/账号权限/工具能力限制），最终为什么选择了 Serverless 托管
- **Flask 到 Serverless Functions 的迁移踩坑**：目录结构问题（`public/` 子目录导致入口文件没有映射到根路径）、项目名配置问题（环境变量缺失导致部署失败的完整排查）
- **一个"看起来是同一个问题"实际是三个不同根因的排查案例**：AI 生成内容随机出现"演示占位文案"，前两次都是误诊（网络问题？超时阈值？），第三次才真正找到根因——这是这个案例里最有复用价值的排查方法论
- **两份代码分开维护的安全实践**：本地硬编码 API Key 快速验证功能 vs 推送到 GitHub 前必须清理敏感信息，两个版本怎么并行维护不互相干扰
- **一周时间线的真实分配**：MVP验证用了多久、迁移公网用了多久、排查稳定性问题用了多久——帮你校准"一周做出AI小产品"里，时间实际是怎么花的，哪些环节最容易低估工作量
